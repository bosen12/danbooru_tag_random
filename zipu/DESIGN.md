# 字鋪 · 設計

排字匣的牌組構築遊戲。深夜的活字鋪：客人上門下委託，你從字盒揀字、排進手盒、付印。
分數到了就成交，那一單最好的一版字會真的送去 ComfyUI 印成一張畫。

跟其他版面一樣掛在 `server.py` 上（`WEB_DIR=zipu`，埠 8795），server 一行都沒改。
`engine.js`、`lexicon.json`、`token_counts.json`、`rules/rating.js`、`sports.js` 靠 SHARED 回退從 `web/` 拿，
**不複製任何一份詞庫或規則** —— 詞庫改了，牌跟著改。抽牌邏輯（`drawOne`）完全沒用到，也沒動。

## 為什麼是牌組構築

詞庫本來就是一套牌規，而且測過了：

| 詞庫裡的東西 | 在牌桌上變成 |
|---|---|
| 四個 section（特徵／服裝／姿勢／場景） | 四種花色：容、衣、姿、景 |
| `mutex`、`contradictions()` | 撞字：同類只能一張，後放進去的燒掉 |
| `era` | 不合時代：一版字投票決定年代，不合的燒掉；三張同一個古代是「同代」 |
| `implies`／`bind` | 附帶：打出和服，自己帶出一個「和服類」，+4 籌碼 |
| `ACT_PLACE`、`NEEDS_CONTEXT`、`CTX_PULLS_*` | 呼應：閱讀＋圖書館、雨＋雨傘，每組 +2 倍率 |
| `SPORT_PRESETS` | 成套：場地＋器材＋服裝 |
| `token_counts.json`（CLIP token 數） | 格數：手盒容量 10 格，字越長越佔位、籌碼越多但每格越不划算 |
| `ratingBlocked(item, "general")` | 牌池：只收全年齡的字 |

生圖慢（一張 5–20 秒）是這類遊戲最硬的限制。這裡生圖只在**成交之後**發生，而且在你逛店的時候背景跑：
玩家永遠不用等 GPU。圖是獎勵，不是題目。

## 一局

- 八章，每章三個委託：散客、熟客、貴客（出難題）。門檻 `[300, 700, 1600, 3600, 7500, 13000, 22000, 35000]`，熟客 ×1.5、貴客 ×2。
- 每個委託：手牌 8 張、付印 4 次、換字 3 次、手盒 10 格。
- 字盒抽空了就「歸字」：印過的鉛字洗回盒裡再抽（36 張的字盒撐不過 4 付印 + 3 換字，而活字鋪本來就這樣周轉）。
- 分數 = 籌碼 × 倍率。牌型給底數；每張計分的字加自己的籌碼；附帶、呼應、道具再加或乘。
- 成交後結帳：報酬 + 剩下的付印次數 + 附加委託 + 利息（每 5 兩 1 兩，最多 5）。
- 商店：三格櫃上（道具、字模、印材）、兩個字包、一個鋪子升級（每章一樣），可重擺、可熔一個字。

### 牌型（最上面的優先）

| 牌型 | 條件 | 底數 |
|---|---|---|
| 時代全版 | 四種花色 ＋ 三張以上同一個古代 | 80 × 7 |
| 成套 | 同一項運動三樣，其中一樣是場地 | 60 × 6 |
| 同代 | 三張以上同一個古代 | 40 × 4 |
| 一色 | 四張以上同一種花色 | 35 × 4 |
| 全版 | 四種花色 | 30 × 3 |
| 三拼／兩拼／散字 | 三種／兩種／一種花色 | 20×2／10×2／5×1 |

字模（中文字體當 Balatro 的行星：宋、楷、隸、仿宋、黑、篆、魏碑、金文）把牌型升級。

### 內容

- **道具 43 個**：加倍率、乘倍率、改容量、重播最後一張、賺利息……每個都有一張烘焙好的靜物插畫。
- **印材 7 種**：燙金、朱印、銅模（牌的加工）、複刻、改刻（換成同一個互斥群的另一個字）、熔爐、錢袋。
- **貴客 12 位**：規則都一句話講完（場景牌不計分、手盒少 4 格、有撞字整版作廢……）。第 8 章的「字鋪東家」一次出兩條。
- **客人 14 位**：各自一句開場白，附加委託從你自己的字盒出題（保證做得到）。
- **起手字盒 3 副**：日常（呼應好湊）、時代劇（同代好湊但要小心不合時代）、運動（成套分數高）。

## 架構

```
zipu/
  pool.js     牌池：詞庫 → 卡牌（花色、格數、籌碼、呼應、成套、插畫 prompt）。零 import，依賴由呼叫端注入
  rules.js    計分：一版字 → evaluate()（撞字、時代、附帶、呼應、牌型）→ score()（一串計分步驟）
  content.js  道具、印材、字模、升級、客人、貴客、字盒、門檻、附加委託
  run.js      一局的狀態機。整局是一個可 JSON 化的物件，亂數狀態也在裡面，所以存檔 = JSON.stringify
  main.js     畫面路由與手勢 → run.js 呼叫；每個改狀態的動作之後存檔
  stage.js    計分動畫：照 score() 的 steps 一格一格播
  print.js    印刷機：run.prints 排隊，一次一張送 /api/gen（SSE），預覽幀只放記憶體
  ui.js fx.js store.js   零件、聲音與小動畫、localStorage
scripts/
  zipu_pool.mjs     牌池摘要；--prompts 給烘焙腳本拿 prompt
  bake_card_art.py  烘焙插畫：走 server.py 的內建工作流，只把 SaveImage 換成「縮圖 → 存 webp」
  test_zipu.mjs     牌池、計分、流程的回歸測試（秒跑完，掛在 test.bat）
  sim_zipu.mjs      平衡模擬：貪心機器人打完整局，統計走到第幾章
```

**計分是純函式，動畫照著它播。** `score()` 回傳 `steps`（牌型底數、每張牌、附帶、呼應、道具、最後總分），
`stage.js` 一步一步把數字加上去。畫面演的就是實際算的，不可能對不上。

**流程從不等動畫。** 所有排程都用 `setTimeout`，WAAPI 動畫只負責好看。分頁在背景、rAF 被停掉時，
`animation.finished` 可能永遠不 resolve —— 遊戲不能卡在那裡。

## 插畫

卡面、道具、客人、背景全部是用你自己的底模事先烘焙的：

```bash
python scripts/bake_card_art.py            # 整本詞庫的卡面（約 1370 張，一張 6 秒，兩個多小時；已有的跳過）
python scripts/bake_card_art.py --extras   # 道具、印材、客人、背景（zipu/art/extras.json）
```

- 卡面放在共用的 `web/cards/`（墨池、排字匣的卡牌模式也吃同一份），字鋪只用得到全年齡那些；
  道具、客人、背景還是放在 `zipu/art/`。prompt 規則在 `web/card-art.js`，`scripts/test_card_art.mjs` 守著。
- 同一顆 seed（1383）、每張照自己的分級配負面詞、832×1216 → 縮成 480×702 webp（約 40KB）。
- 每一類字用一種鏡頭：髮色髮型上半身、眼睛臉部特寫、服裝全身、動作配上它的地點、場景是無人風景、物件是靜物。
  試生 20 張之後定的（見 `pool.js` 的 `PERSON_FRAME`、`STILL_LIFE`）。
- 插畫 prompt 會帶上這張牌會附帶的字（籃球場＋室外），畫出來才跟打出去的效果一致。
- 產物不進版控（取決於底模）。沒烘焙過的牌用鉛字版卡面：大大一個字。

**卡面的招牌：左邊是直排書脊。** 手牌放不下時會像撲克牌一樣疊起來，只露出左邊 —— 所以花色印、
直書的字名、籌碼全放在左緣的書脊上，疊得再密也讀得到。中文直排在這裡剛好是答案。

## 平衡

`node scripts/sim_zipu.mjs 60`。機器人只會挑眼前最高分的一版、買得起就買道具，不懂連乘，也不用印材。
目前它平均走到第 5～5.6 章，偶爾摸到第 8 章；懂得湊呼應、把乘法道具擺在右邊的人打得穿。
改門檻或道具數值之後重跑一次。

## 分級

牌池只收 `ratingBlocked(item, "general")` 放行的字，再剔掉一批全年齡但不適合做成卡的字（身體部位特寫、
學生制服、兩人才成立的動作、脫衣場所，見 `pool.js` 的 `EXCLUDE_*`）。插畫和成品都用全年齡負面生成。

## 不做

- 連線對戰、排行榜
- 跳過委託換獎勵（Balatro 的 skip tag）
- 多人輪流
